# API assistants

In **Settings → Zusia → Assistants**, open **Ollama API**, **Unsloth API** or **OpenAI-compatible API**. Set the base URL including `/v1` (HTTPS for remote hosts; HTTP is allowed only for `127.0.0.1`, `localhost` or `::1`), choose authentication, and save the API key if required. Then click **Check connection and list models**, select the exact model ID and choose that assistant under **Answer with**.

- Ollama defaults to `http://127.0.0.1:11434/v1`, with no authentication for its local API.
- Unsloth defaults to `http://127.0.0.1:8888/v1`; create an API key in Studio's **Settings → API**. Select a downloaded chat model: Zusia loads it through Studio's native API before answering, without enabling Studio's global **Switch model by request** setting. You can also use **Load model** in Zusia's settings; **Stop loading** cancels only the load started by Zusia. If memory is insufficient, adjust the provider profile or the per-model overrides and retry.
- **Provider profiles are the default for Unsloth and Ollama.** Zusia reads Unsloth's saved per-model/variant launch settings, or Ollama's model/tag parameters, and checks the actual per-request context before selecting document excerpts. It does not use the model's theoretical maximum as the active context budget.
- **Customize in Zusia** adds optional overrides saved separately per endpoint and model; empty fields inherit the provider. Context and sampling are supported for both providers; Unsloth additionally supports GGUF variant, KV cache dtype, GPU layers and parallel slots. Ollama weight quantization follows its selected model/tag; its GPU and KV-cache configuration stay server-side. Ollama uses native `/api/chat` with NDJSON so context overrides apply to every tool round, not just model warmup. Prompt, document tools and maximum response budget remain controlled by Zusia.
- **Read provider profile** inspects settings without loading a model. **Load model** applies them without generating an answer. Saved Unsloth command-line flags are not imported; browser-only settings that Unsloth does not persist server-side are not available through this integration. Older Unsloth versions without a profile endpoint use server defaults and report that saved presets are unavailable. Profile authentication failures remain visible. Document mode requires at least 8,192 effective context tokens.
- Native provider profiles require access to the server's `/api` routes as well as `/v1`; reverse proxies must expose both under the same prefix. For a server exposing only OpenAI-compatible routes, use the generic OpenAI-compatible assistant and configure its context budget manually.
- Custom endpoints use the OpenAI **Chat Completions** protocol (`/chat/completions`), with `/models` for discovery. You may enter a model ID manually if discovery is unavailable. Other native API dialects need their own adapters.

Model selections are saved per endpoint and survive restarts. Empty or invalid model edits keep the previous valid selection; changing to another endpoint restores that endpoint's model or asks you to choose one. Keys remain scoped separately to the endpoint.

For Unsloth and Ollama, **Document tools**, **Image input** and **Reasoning effort** default to **Detect from provider**, with explicit enable/disable overrides per endpoint and model. Unsloth exposes capabilities once the model is loaded; Ollama exposes them through `/api/show`. Unknown capabilities stay disabled. The reasoning menu follows the model's advertised boolean controls or named levels, including its provider default. Existing explicit enabled settings are preserved. Generic OpenAI-compatible endpoints retain manual capability switches. Document tools only search this document, read up to three pages at a time and fetch its outline, for at most four tool rounds. Models without tool calling still get selected excerpts automatically.

The chat's expandable model status shows the selected and running model, weight quantization, effective context and last-check time. Visible chats refresh native status every 12 seconds, with a manual refresh action; these checks never load or switch a model. Authentication, connection, model, memory, context and interrupted-answer errors have specific recovery guidance. A partial interrupted answer is marked incomplete and is not saved as a completed reply. Failed generations are never replayed automatically.

Zusia selects relevant excerpts with BM25, reserving room for the output and document tools. Unsloth's `/v1/chat/count_tokens` can count the full text prompt with its actual tokenizer. When that route is available, Zusia can include more evidence and recounts the expanded prompt before sending it. Older servers, unavailable tokenizers, images and providers without a supported counting route use the conservative UTF-8 budget, labelled as an estimate. A tokenizer reporting a different running model stops the request. Long chats carry their reading memory and recent exchanges that fit; they do not assume a server-side conversation.

Expandable request details show provider-reported input/output/cache counters and native timings when available, alongside the context budget source, reserved output, preparation time and generation rounds. Throughput uses provider generation time when reported; otherwise it is explicitly labelled as a request average including processing and network time. Missing provider counters remain missing. Reasoning text is used only internally when replaying tool calls and is not displayed or saved in chat history. Turn off **Stream answers** if your endpoint or proxy cannot stream.

Saved reasoning choices are retained while capabilities are being discovered after startup, then checked against the prepared endpoint and model before sending. Background memory updates and section summaries are built using that same effective context, including 8,192-token profiles and unavailable tokenizers. Small memory batches keep complete question/answer pairs; orientation text and large summary merges are bounded to leave room for the task and output. Section summaries retain their prose output format.

Within one Zotero instance, Unsloth requests sharing an endpoint keep their model/profile active through the entire answer and tool loop. Matching requests can generate in parallel; a different model or a settings-driven reload waits in order until the current group finishes. Stop cancels a queued request before accessing its key or loading its model; plugin shutdown cancels active and queued API work. Reasoning uses the capabilities captured during preparation for the whole request, even if the discovery cache expires while tools run. Changes made directly in the provider remain outside this coordination.

API keys are separate from normal preferences. On versions exposing Zotero's OS key store, keys are encrypted there; on older versions they stay in memory for the session and must be entered again after restarting. Endpoint changes require their own key. A connection check lists models without starting an inference.

Protocol references: [Ollama compatibility](https://docs.ollama.com/api/openai-compatibility), [Unsloth API](https://unsloth.ai/docs/basics/api). Streaming uses bundled **eventsource-parser 4.1.3**, built with **esbuild 0.28.2** for Firefox 115 and later; no CDN or Node runtime is needed in Zotero.

## Background calls

Ollama and Unsloth retain the existing reading-memory behavior. Custom endpoints make no automatic memory or section-summary calls until **Allow background calls** is enabled in that endpoint's assistant card. These calls can cost money. Consent is scoped to the endpoint and is cleared when its URL changes; the Memory sheet still controls whether memory updates and section summaries run.
